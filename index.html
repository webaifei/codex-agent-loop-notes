01

三层 loop

代码：code/step1.mjs code/step2.mjs
对照：codex-rs/core/src/tasks/regular.rs（第一层）、codex-rs/core/src/session/turn.rs:424-660（第二层）

我原以为 agent 就是一个循环

问模型，执行工具，再问模型——不就是一个 while 吗。

这个理解对了一半。码农写爬虫是这样的：一层循环，条件写清楚就行。但 agent 的循环有一个特点——它自己不知道自己要不要继续。那个答案在模型那边，得问完才知道。

于是就变成了三层。

第一层：还有没有用户的活

tasks/regular.rs 里的 RegularTask::run，整个 agent 的入口：

出口只有一个：队列空了。

用 Node 写出来是 code/step1.mjs：

用户在模型干活时补的那一句，没有插进第一轮，而是等第一轮结束、hasPendingInput() 发现队列里还有东西，才开了第二轮。

这就是 next_input = Vec::new() 那一行的含义：第二轮不复用最初的输入，它去队列里领。

第二层：模型还要不要再来一次

regular.rs 每转一圈都会调用 run_turn。而 run_turn 里面还有一个 loop。

两个 loop 长得很像，问的却是两件事：

  • 外层问：还有没有新的活
  • 内层问：这一趟活干完了没有

内层要处理的情况很具体：模型说"我得先读一下 parseDate.ts"，读完才能改。读了文件不是结束，是这一轮里的第一步。

一个布尔，省掉了多少判断

把两件事合成一个 needs_follow_up，看起来只是省了几行。但它带来的效果是：内层循环只有一个出口，而且那个出口是提前算好的。

对比一下 DeepSeek Harness 的写法：

两个条件分开写。DSH 需要这样做，因为它的 turn/end 事件要记原因——是正常结束、撞了 token 上限、还是被用户中止。那是一个枚举，不是一个布尔。

Codex 不需要区分这些的时候，就把它们压成一个布尔。

循环的层数不重要，重要的是每一层在等什么。 层数和布尔值都是表象，出口条件才是本体。

一个容易踩的坑

写 step2.mjs 的时候我踩了一个：假模型按"第几个 step"来决定要不要继续，但 stepContext 在两次 step 之间是复用的（Codex 的 next_step_context），所以那个变量永远不变，循环停不下来。

真实系统里不会出这个问题——模型根本不知道自己是第几个 step，它只看对话历史。这个 bug 恰好说明了一件事：step 是循环的记账单位，不是模型的输入。

下次再看到一段 agent 代码，先别读它调了什么模型、用了什么工具。先找 loop，看它的条件是什么、谁在里面改这个条件。

02

输入的两种来源

代码：code/step3.mjs
对照：codex-rs/core/src/session/input_queue.rs

我原以为队列就是用户消息排队

一个数组，先进先出，主循环从里面取——这是我一开始对输入队列的全部想象。

直到看见 Codex 的 InputQueue 里有 steer、mailbox、deferred 三种东西。

它们不是"不同优先级的用户消息"。它们是来源不同的两种活：一种来自你（用户插话），一种来自别的 agent（子任务干完回报）。

为什么不能混在一起

先看一个具体场景。

你让 codex 修一个 parseDate 的时区 bug。同时你另开了一个子 agent，让它顺手把 utils/date.ts 重构一下。

主任务跑到一半，子 agent 干完了，发来一条消息："我改完了 utils/date.ts"。

现在问题来了：这条消息该现在插进来，还是等你这一轮跑完再说？

两个答案都对，取决于产品想怎么做：

  • 现在插进来：主任务下一步就能看到 utils 已经改好了，可能就不用自己动手
  • 等下一轮：这一轮的中途上下文保持干净，不会被外部变更打断

既然两个答案都对，就不能由队列自己决定。Codex 的做法是把选择权交给调用方，并提供一对显式动词（input_queue.rs）：

code/step3.mjs 把两种情况跑在一起：

选择延迟：

选择接受：

同一条消息，一个落在下一轮的起点，一个落在当前轮的第二步。

同一条消息该塞进当前轮还是下一轮，是两个不同的产品行为。 代码上的差别只是一个方法调用，用户感受到的差别是"它有没有听懂我刚才说的"。

一个布尔和它差点骗过我

写这一步的时候我搞出了一个死循环。

判断"要不要再来一步"的时候，我用了一个会把 deferred 也算进去的方法。结果那条被延迟的消息一直在队列里，needs_follow_up 就一直为真，内层循环转了几万圈，Node 直接把内存撑爆。

原因说破了很简单："这一步还有没有新输入"和"整个任务还有没有活"是两个问题。

  • 这一步有没有新输入 → 只看 steer 和未被延迟的 mailbox
  • 整个任务还有没有活 → 包括 deferred

Codex 里这是两个不同的方法（get_pending_input 和 has_pending_input）。我图省事合成一个，循环就停不下来了。

这个错误值得记下来，因为它不是笔误——它是把一个不等价的判断当成了等价的。

判断条件不能有副作用

同一个 bug 里还有个更隐蔽的地方。

我最初写的判断长这样：

getPendingInput() 是会把消息取走的。写在判断条件里，等于每次检查都把队列清空一遍——检查行为改变了被检查的对象。

改成只读的 countPendingInput() 之后才对。

真实系统里这类错误特别难查：代码能跑，逻辑看起来对，只是消息偶尔"莫名其妙地消失了"。

到这里你应该能看出 InputQueue 那 810 行在防什么了：防的不是"消息丢了"，是"消息在错误的时候出现"。

03

重试之前先分类

代码：code/step4.mjs
对照：codex-rs/core/src/session/turn.rs:1663-1759

我原以为重试就是失败后重发

网络请求会失败，重试几次就好了——这是写爬虫留下的肌肉记忆。

放到 agent 上，这个直觉会让你在"上下文超长"的时候白打三次请求，每次都在烧钱。

两类不该重试的错误

turn.rs:1715 那段 match 是这一步的全部内容：

两类错误立刻返回，一次都不重试：

  • 上下文超限——再次发出去还是同一份超长上下文，结果不会变
  • 额度用尽——再试一百次额度也不会回来

剩下的才交给重试逻辑。

注意这两条不只是"提前 return"。它们还顺手更新了会话状态：一个把 token 上限标记为满，一个刷新了限流信息。失败也是一种信息，要用起来。

重试次数由谁定

不是在循环里写死一个 3，而是问 provider 要。

这个细节在产品上的意义：不同模型提供方的稳定性、限流策略、计费方式都不一样。有的允许你多打几次，有的打一次就计一次费。把这个数字交给 provider，是承认"重试几次合适"是外部知识，不是循环该知道的事。

DeepSeek Harness 做的是同一件事，只是走的是另一条路——它把 retryPolicy 作为参数传给错误处理事件，让监听器决定。

跑起来看

code/step4.mjs 跑了两个场景：

最后那行对比是这个练习的重点。两个场景都是"请求失败"，但一个值得再来两次，一个一次都不该来。

重试的前提是：再来一次真的可能成功。 分类就是为了回答这个前提成不成立。

分类靠什么

注意 err.details()。

Codex 不是去匹配错误消息里的字符串，而是错误对象自己带一个 details 判别字段。上面那段 match 就是在这个字段上做穷尽匹配。

这个设计的价值在改动的时候体现：新增一类错误，编译器会提醒你 match 没覆盖全。而如果靠 err.message.includes('context')，漏掉一个分支只会在线上以"重试了三次还是失败"的形式出现。

用类型承载分类，而不是用文本。 文本是给人看的，判别字段是给机器看的。

下次写重试逻辑的时候，先别急着 for (let i = 0; i < 3; i++)。先问一句：哪些失败是再来一次有意义的？

04

取消怎么传播

代码：code/step5.mjs
对照：codex-rs/core/src/session/turn.rs:1709,1742-1743（child_token / or_cancel 的用法）

我原以为取消就是一个标志位

按了 Ctrl+C，把 isCancelled 设成 true，然后每个循环自己检查一下——听起来够用了。

问题在于"每个"到底有多少个。一次采样请求在等网络，一个工具子进程在跑测试，一轮对话在等收尾，一个子 agent 在后台干活。你要记得在每一个地方检查那个标志位，漏一个就会有一个任务在后台永远转下去。

Codex 换了个方向：不是让每个地方去查，而是让取消自己传播下去。

从父到子派生

turn.rs 里有这么一行（L1709）。它从当前的取消令牌派生出一个子令牌，交给这一次步骤使用。

关键在父子关系：父令牌一旦取消，所有子令牌自动跟着取消。

跑一下 code/step5.mjs：

只取消这一轮：

取消整个任务：

三种粒度，一个动作。你不需要遍历所有正在跑的任务去通知它们——它们挂在同一棵树上。

为什么这件事在 agent 上特别重要

因为 agent 的任务是用户随时可能反悔的。

写个批处理脚本，取消了重跑一次就行。但 agent 跑一半被取消，已经花掉的 token、已经改了一半的文件、已经发出去的子 agent，都是有成本的。

所以"取消"在这类系统里不是异常路径，是正常路径。正常路径就值得用结构化的方式表达，而不是一个到处传的布尔。

谁先到用谁

turn.rs L1742 还有一行：

or_cancel 是个组合子：任务先完成就用任务的结果，令牌先取消就抛取消。

这解决了取消里最难写对的地方。手写通常是：

然后忘了处理 task 在输掉竞争之后还在后台继续跑的情况——它没被真正停掉，只是没人听它说话了。

or_cancel 把这个语义封成一个操作符，写在调用点上，一眼能看出"这里有取消点"。

我的实现偷了个懒

code/step5.mjs 里我用 AbortController 手写了 CancellationToken：取消时先 abort 自己，再遍历 #children 逐个取消。

真实的 Rust 版本不需要遍历——tokio 的令牌是一棵树，取消时原子地向下传播。

不过这个"偷懒"本身有教学价值：父子传播的语义是核心，遍历还是原子操作是实现细节。 看懂前者，换任何语言都能重新实现。

下次设计任何"用户可以中途叫停"的东西，别从标志位开始。先问一句：这件事有哪些层次，取消应该从哪一层往下传？

05

事件流不是分片的答案

代码：code/step6.mjs
对照：codex-rs/codex-api/src/common.rs 的 enum ResponseEvent、turn.rs:2658（消费循环）、turn.rs:2967（Completed 分支）

我原以为流式就是把答案分几次发过来

一句话切成三块，客户端拼起来——这是 fetch 加 SSE 给人的直觉印象。

所以我第一次看到 ResponseEvent 有十几个变体的时候，以为只是厂商话多。

不是。它传的不是"答案的碎片"，是"正在发生的事"。

事件流里有几类东西

Codex 的 ResponseEvent 里，除了文本还有：

注意最后那几类——它们跟"答案"没关系。

RateLimits 是配额，ServerModel 是路由信息（服务端可能把你请求的模型换成另一个），ReasoningContentDelta 是模型的思考过程。这些都不进最终消息，但都必须在流里传，因为只有流经过的地方才知道这些事。

事件流不是分片的答案，是正在发生的事。 答案只是其中一类事件攒出来的结果。

攒的过程

code/step6.mjs 把三种事件的处理都打出来了：

文本是一点点攒的，但消息只在一处产生——OutputItemDone。中间那些 delta 是给界面看的，最终那条消息由 Done 事件携带的完整 item 决定。

这和 DeepSeek Harness 的 block-end 是同一个设计：delta 用于渲染，完整的 item 用于记账。

工具参数也是片段

工具参数是一串 JSON 文本，被切成碎片发过来，得按 item_id 拼起来才能 JSON.parse。

这里 Codex 和 DSH 有个小差别，值得一提：

Codex DSH
用什么标识一个调用 item_id + call_id index
文本 OutputTextDelta(String)，无下标 { index, text }

Codex 用 id——因为一条响应里可能并行产生多个工具调用，用序号容易串。DSH 用 index，因为它的 chunk 携带了块的下标，语义上等价于"第几个块"。

两种都能work，但 id 在并行场景下更难写错。

end_turn 可能不存在

这是我在这一步最有收获的地方。

Completed 事件里带一个 end_turn: Option<bool>。而源码注释写着：

Did the model affirmatively end its turn? Some providers do not set this, so we rely on fallback logic when it is None.

也就是说："模型说完了没有"这个判断，不能依赖服务端一定会告诉你。

step6.mjs 的第三个场景专门跑这个：

兜底规则很简单：如果服务端没表态，而且这一轮没有产生工具调用，那就当作说完了。

这个规则为什么成立？因为如果模型要调工具，它必然产生一个 function_call item。没有工具调用又没有明确的"还没完"信号，继续问下去也只是得到同样的回答。

真实的工程代码里到处是这种**"信息可能缺失，但我得给个说法"**的地方。它们不会出现在架构图里，只会出现在注释里。

三种判定的优先级

把 step6.mjs 里的判断逻辑抽出来，顺序是这样的：

  1. 有工具调用 → 必须继续（工具结果得送回去）
  2. 服务端明说了 end_turn → 听它的
  3. 服务端没说，也没有工具调用 → 判定完成

第一条优先级最高，因为它是一个事实——模型确实产生了一个还没被满足的调用。而 end_turn 是个声明，声明可能缺失，也可能有别的解释。

先信事实，再信声明，都没有才走兜底。

下次再看到"流式响应"，先问一句：这条流里除了答案还在传什么？那些不构成答案的事件，往往才是这个系统真正在意的状态。

06

让模型写程序调工具

代码：code/step7.mjs
对照：codex-rs/code-mode-protocol/src/runtime.rs（协议）、codex-rs/code-mode-runtime/src/v8_init.rs（V8 执行）

我原以为工具调用只能一次一个

模型说"我要调 grep"，你执行，把结果给它；它再说"我要读那个文件"，你执行，再把结果给它。

这是最直观的做法，也是 Codex 和 DeepSeek Harness 都支持的默认模式。

但它有个成本问题：每一次工具调用都要一次完整的模型往返。 找一处用法、读那个文件、数行数——三个工具调用就是三轮模型请求。

而这三步之间有依赖关系，模型必须看到上一步的结果才能决定下一步，所以合并成一次并行调用也不行。

换个思路：让模型写程序

模型不是会写代码吗。

那就不给它三个工具，给它一个能调用这三个工具的程序：

一段程序，一次往返，三步全做完。

与其教会模型用工具，不如让它写程序。 前者要教 N 遍（每个工具的 schema、参数、什么时候用），后者它已经会了。

code/step7.mjs 把两种模式的区别摆在协议层：

注意 ExecuteRequest 的形状：模型发的是 source（程序源码），不是 tool call。 同时附带 enabled_tools——宿主告诉运行时段代码里能调用哪些工具。

程序会跑很久，所以 cell 要能挂起

上面这段程序运气好，几十毫秒跑完了。但如果 read_file 卡了十秒呢？总不能把整轮对话堵死。

Codex 的答案是 cell 可以挂起。协议里有三个动词：

execute 会一直等，直到 yield_time_ms 用完。程序还没跑完，就返回一个 Pending：

pending_tool_call_ids 这个字段是关键：它不是"程序还没跑完"，而是"程序正卡在 call_3 这个调用上"。

宿主拿到这个信息后有两个选择——把控制权交回给模型（让模型决定要不要等），或者自己继续 wait 同一个 cell。挂起的是 cell，不是对话。

这在架构上的意义：一段正在跑的程序，变成了一个可寻址、可恢复的对象。它有 id（cell_id），有状态（pending 哪些调用），可以被别的环节查询和续跑。

另一种答案：一次跑完

DeepSeek Harness 的 PTC 解决同一个问题，但选了另一条路：程序一次跑完，不挂起。

工具通过一个全局命名空间暴露（tools.grep(...)），是普通的 async 调用，runtime 负责把调用桥接到宿主。程序要么跑完，要么失败。失败不是抛异常，而是结果里的一个字段：

而且它明确写着：每次运行都不会保留之前程序的状态。 要共享状态得靠别的机制，不能指望上一段程序留下的变量。

两种答案，在权衡什么

Codex code mode DSH PTC
执行环境 内嵌 V8 独立 Node / CPython 进程
生命周期 可挂起、可恢复（cell_id） 一次跑完
中间状态 保留在 cell 里 不保留
隔离方式 同进程 V8 隔离 进程级 + 沙箱策略
引擎启动 快 慢（要起进程）

Codex 换来的是"程序可以等"。 V8 在同一个进程里，启动几乎免费，所以可以随时起一个 cell、挂起、恢复。

DSH 换来的是"程序跑在真正的隔离里"。 独立进程能用操作系统的沙箱（Landlock、Seatbelt），代价是每次运行要起一个新进程——所以它干脆不保留状态。

这不是谁更先进的问题，是两个不同的约束推出来的两个不同的解：一个优先"交互的连续性"，一个优先"隔离的强度"。
